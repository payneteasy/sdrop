# Payneteasy Secrets: client format

What a client must do to create and read one-time secrets. The browser client and `sdrop` follow
this document and are checked against the same test vectors (`spec/`). The server stores only the
encrypted envelope and never sees the key, the passphrase or the plaintext.

## 1. Keys

- `K_url`: 32 random bytes generated by the client. It travels only in the URL fragment (`#…`) as
  base64url without padding (43 characters) and never reaches the server.
- `salt`: 16 random bytes, stored in the envelope header.
- Optional passphrase (a second channel: the link one way, the passphrase another):
  - `P = PBKDF2-HMAC-SHA256(UTF-8(NFC(passphrase)), salt, 600000 iterations, 32 bytes)`
  - `ikm = K_url || P`
- Without a passphrase: `ikm = K_url`.
- `K_enc = HKDF-SHA256(ikm, salt, info = "secret-drop v1 aes-256-gcm", L = 32)`.

A passphrase consists of Unicode scalar values only (before NFC) and is never empty.

## 2. Envelope

```
offset  size  field
0       4     magic = "SDRP" (0x53 0x44 0x52 0x50)
4       1     version = 0x01 (text or file) or 0x02 (text and files, section 4)
5       1     flags: bit0 = passphrase; other bits are 0
6       16    salt
22      12    iv (random)
34      N+16  AES-256-GCM(K_enc, iv, plaintext, aad = bytes 0..33): ciphertext with the tag
```

The whole 34-byte header is the AAD, so the passphrase flag and the version are authenticated.
Valid envelope length = `34 + bucket + 16`: one of 1074, 4146, 16434, 65586, 262194, 1048626.

## 3. Plaintext and padding

```
u32 BE  len: length of the JSON header in bytes
len     JSON in UTF-8: {"kind":"text","text":"..."}  or  {"kind":"file","name":"...","size":N}
size    file only: exactly N bytes of the file
...     zeros up to the bucket size
```

- Buckets: 1024, 4096, 16384, 65536, 262144, 1048576 bytes. The smallest bucket that fits
  `4 + len` (text) or `4 + len + size` (file) is used. The service may set a lower limit
  (`GET /api/limits`, section 6).
- `kind` is `"text"` or `"file"`; there are no other fields or values in version 1. New fields
  or kinds come only with a new `version` (section 4).
- File `name`: a non-empty string of up to 255 bytes of UTF-8 (Unicode scalar values), without
  U+0000–U+001F, U+007F, `/`, `\`, not `.` and not `..`; on creation the client takes the base
  name and replaces forbidden characters with `_`. `size`: an integer from 1, decimal, without
  leading zeros. No content type is sent: the recipient always gets the file as
  `application/octet-stream` and never opens it.
- **Canonical encoding** (the test vectors depend on it): exactly
  `{"kind":"text","text":<string>}` or `{"kind":"file","name":<string>,"size":<number>}`, in this
  field order, without spaces. Strings are escaped as `JSON.stringify` and `serde_json` do:
  `"` → `\"`, `\` → `\\`, `\b \f \n \r \t`, other U+0000–U+001F → `\u00xx` in lowercase hex;
  everything else, including `/`, U+007F and non-ASCII, as is in UTF-8. Empty text and text with
  unpaired surrogates are rejected on creation.
- **Checks on decryption** (any violation: "damaged secret", nothing is shown): envelope length;
  magic, version, unused flag bits; the GCM tag; `len <= bucket − 4`; the bucket is the smallest
  that fits the content (a larger bucket is rejected); zero bytes after the text or after the file
  data; strict UTF-8 JSON (no BOM); **only the canonical encoding** is accepted. Text: the JSON
  starts with `{"kind":"text","text":`, ends with `}`, and the string between them decodes to a
  non-empty string that re-encodes canonically to the same bytes. File: starts with
  `{"kind":"file","name":`, ends with `}`, the rest is split at the **last** `,"size":` into the
  name string (same rules) and the decimal `size` (`[1-9][0-9]{0,7}`); `4 + len + size <= bucket`.
  Any other JSON form (other escapes, spaces, order, extra or repeated fields, nesting) is an
  error. This keeps different JSON parsers from disagreeing.

### Decryption order and errors

Checks run in this order; the first failure decides the error code:

1. Header without the key: envelope length, magic, version (1 or 2), unused flag bits →
   `corrupt`.
2. The envelope has the passphrase flag but no passphrase was given → `need_passphrase`. The
   envelope can be decrypted again once the user enters it.
3. Key derivation and the GCM tag: a wrong passphrase, a wrong key or a modified envelope →
   `decrypt_failed`. If a passphrase was used, the client should let the user try again with the
   envelope it already has: the server deleted it on consume.
4. Plaintext checks of sections 3 and 4 → `corrupt`: nothing is shown, the secret is lost.

## 4. Text and several files (version 2)

One link can carry a text and up to 20 files. The envelope has `version = 2`; the plaintext layout
is the same (`u32 len | JSON | data | zeros`) with the header

```
{"kind":"bundle","text":<string>,"files":[{"name":<string>,"size":<number>},…]}
```

- File data follows the header in the order of `files`, then zeros up to the bucket. The bucket is
  the smallest that fits `4 + len + Σsize`.
- `text` may be empty; `files` has 1 to 20 entries; `name` and `size` follow the file rules of
  section 3 (names may repeat).
- One secret, one record: no files → `text` (v1); one file and empty text → `file` (v1);
  otherwise `bundle` (v2). On decryption, `bundle` with one file and empty text is an error, as
  are `bundle` in a v1 envelope and `text`/`file` in a v2 envelope.
- Canonical check: the header is accepted only if rewriting the decoded value in the canonical
  form (field order as above, no spaces, strings per section 3, decimal numbers without leading
  zeros) gives exactly the same bytes.
- Clients that know only version 1 answer "damaged" on a version 2 envelope after it has been
  consumed, so the secret is lost: keep clients up to date.

## 5. Links

| Path | Meaning |
|---|---|
| `/s/<id>#<K_url>` or `/s/<id>#<K_url>~p` | recipient link; `~p`: the secret has a passphrase |
| `/o/<id>#<ownerToken>` | sender link: status and revoke |

- `id`: 64 lowercase hex characters.
- Recipient fragment: exactly 43 base64url characters, then an optional `~p` suffix. After
  decoding, the key is exactly 32 bytes and encoding it again gives the same string; anything else
  is "broken link", with no API requests. `ownerToken` is parsed the same way.
- The suffix only lets a client ask for the passphrase before consuming. The source of truth is
  the authenticated envelope flag: if the envelope needs a passphrase and there was no suffix, the
  client asks after fetching; if there was a suffix and the envelope has no flag, the passphrase is
  not used.

## 6. HTTP API

Every `/api/*` request carries `X-Secret-Drop: 1`; the API allows no CORS, and a request that
changes something is refused if it carries an `Origin` other than the service's own (clients
outside a browser send none). Responses carry `Cache-Control: no-store`; 401 and 403 mean the
service's login does not allow the request. Times are ISO 8601 strings in UTC with
milliseconds (`2026-10-22T12:00:00.000Z`). A service behind Cloudflare Access answers an
unauthenticated request with a redirect; clients do not follow it (the request never reached the
service, nothing was consumed), obtain an Access token (`cf-access-token` header) and retry once.

- `GET /api/limits` → 200 `{"maxBucket": N}`: the largest bucket the service accepts. Clients
  check it before encrypting.
- `POST /api/secrets?ttl=<seconds>`, body: the envelope, `Content-Type: application/octet-stream`.
  `ttl` is 3600, 86400 (default) or 604800; another `Content-Type` is 400. → 201 `{"id": string, "expiresAt": string,
  "ownerToken": string}`: `id` as in section 5, `ownerToken` 43 base64url characters (32 bytes);
  400 for a malformed envelope or `ttl`; 413 `{"error":"too_large","maxBucket":N}` above the
  service limit; 429 when creating too often.
- `POST /api/secrets/<id>/consume` → 200 with the envelope; the server deletes it at the same
  moment, so a secret is delivered at most once. If the connection breaks during this request, the
  result is unknown: the secret may already be gone. Not found, already read, revoked, expired and
  invalid id all give the same 404.
- `GET /api/secrets/<id>/status` with `Authorization: Bearer <ownerToken>` → 200
  `{"state": "stored" | "consumed" | "revoked", "createdAt": string, "expiresAt": string,
  "consumedAt"?: string, "consumedBy"?: string}`; `consumedAt` is present once read, `consumedBy`
  (the reader's email) only on a service with login. A wrong token gives the same 404.
- `DELETE /api/secrets/<id>` with `Authorization: Bearer <ownerToken>` → 204 (revoked, repeat is
  fine), 409 with the status body if already read, 404 otherwise.

How to use all this in your own client, step by step: [CLIENTS.md](CLIENTS.md).

## 7. Test vectors

- `spec/vectors.json`: `{name, k_url, salt, iv, passphrase|null, <secret>, bucket,
  envelope_hex | envelope_sha256}` where the secret is `text`, `text_repeat: {char, count}`,
  `file: {name, data_hex | data_seed + size}` or `bundle: {text, files: [...]}`. Encrypting with
  the given `salt` and `iv` must give the envelope; decrypting must give the secret.
- Compact vectors (buckets from 262144): file bytes from `data_seed` are the concatenation of
  `SHA-256(UTF-8(seed + "/" + offset))` for decimal offsets `0, 32, 64, …`, cut to `size`; the
  envelope is given as `envelope_sha256` (hex SHA-256 of the whole envelope).
- `spec/vectors-invalid.json`: `{name, k_url, passphrase|null, envelope_hex, error}` with `error`
  one of `corrupt`, `decrypt_failed`, `need_passphrase`. Every implementation must reject them
  with exactly that error.
- `spec/links.json`: valid fragments with the key in hex and rejected ones.
